2现状与差距

A 批让 read_page / find / form_input / computer 覆盖了所有 frame，但还有三个工具留在主 frame。

工具现状差距场景
get_page_text只主 frame正文在 iframe 里的页面（嵌入式文档、富文本预览、三方组件）读到空或残缺
javascript_tool只主 frame想探查某个 iframe 的 DOM / 变量，只能手写 window.frames[i]，跨域 frame 直接拒绝
file_upload拒绝子 frame上传控件在 iframe 里（支付收银台、老后台）时直接报错，无法继续
intercept_add body只文本Mock 图片、字体、PDF 等二进制资源做不到
intercept_add CORS不带凭据带 cookie/token 的跨域 fetch 被 Mock 时，响应缺 allow-credentials，浏览器拒收

frame 路由示意：ref 前缀已经存在

主 frame（frameId 0）· http://a.com
按钮 ref_12 · 输入框 ref_13
子 frame（frameId 3）· http://b.com（跨域）
上传控件 f3.ref_7 · 正文文本（get_page_text 目前读不到）

A 批已建好这套前缀路由（read_page / find 的输出里，子 frame 元素都带 f<frameId>. 前缀）。C 批只是让剩下三个工具也认得它。

3三个工具怎么改

入口方式统一：能定位元素的用 ref 前缀路由；纯"对哪一层执行"的用新参数 frameId。

工具怎么指定 frame行为
get_page_text新参数 frameId（可选）不传＝现状（主 frame 正文）。传了＝只提取那个 frame 的正文。另加 allFrames:true 合并所有 frame 的文本，各段带 frame 标头
javascript_tool新参数 frameId（可选）不传＝主 frame（现状）。传子 frame 的 id＝在该 frame 上下文执行，location、document 都是那个 frame 的
file_uploadref 本身带前缀，无需新参数ref: "f3.ref_7" 直接可用：在对应 frame 里找 input、设文件；触发式（triggerRef）同理

4拦截增强

两个 B 批明确记录的限制，都在 lib/intercept.js 纯逻辑层解决。

二进制响应体

intercept_add { tabId: 101, urlPattern: "*/avatar.png*", action: "fulfill",
                 status: 200, headers: { "content-type": "image/png" },
                 bodyBase64: "iVBORw0KGgoAAAANSUhEUg…" }

Rule r4 added  */avatar.png*  ->  fulfill 200, 1 header, body 4.2 KB (binary)
  • 新字段 bodyBase64：内容就是 base64，原样交给 CDP（CDP 的 Fetch.fulfillRequest 本来就收 base64，浏览器侧零改动）
  • 与 body 互斥，同时传报错；解码后大小上限沿用 1 MB
  • 入库前校验 base64 合法性，坏输入在 intercept_add 就报错，不会等到请求命中才失败
  • intercept_list 对二进制 body 显示字节数，不显示内容

带凭据的跨域 Mock

1 跨域 fetch 带 cookie页面请求 credentials:"include"
→
2 Mock 响应补头自动加 access-control-allow-credentials: true
→
3 浏览器放行页面正常拿到 Mock 数据
  • 请求带 Origin 且响应需要凭据时，自动补 access-control-allow-credentials: true（allow-origin 保持回显 Origin，不用 *——规范禁止 * 与 credentials 同用）
  • CORS 预检的自动应答同样补这个头
  • 规则自己写了 CORS 头时不覆盖，以规则为准

5默认选择与风险

我替你做的默认选择（可推翻）
  • 不新增工具，全部是既有工具的增强，接口向后兼容
  • frame 定位用 ref 前缀优先，纯执行类的加 frameId 参数
  • get_page_text 默认行为不变（主 frame），合并模式要显式传 allFrames:true
  • 二进制 body 用独立的 bodyBase64 字段，不复用 body（类型语义清晰，出问题好排查）
  • allow-credentials 自动补，仅当跨域且请求真的带凭据特征时
  • 老工具实现从 background.js 搬进 lib/ + tools/ 分层，与 B 批结构一致
风险与待验证
  • DOM.setFileInputFiles 对子 frame 节点的定位方式需要实验证实（页面级 CDP 命令，子 frame 的 DOM 树要拿到正确的执行上下文）
  • javascript_tool 的 CDP 兜底在子 frame 的行为（Runtime.evaluate + frame 定位）需要实测
  • file_upload 触发式（intercept file chooser）在子 frame 点击时，点击坐标换算复用 A 批的跨域握手，理论上没问题，仍要手测
  • 大 body 的 base64 在 Service Worker 与 WS 链路上的体积（1 MB base64 约 1.4 MB 文本）要过一遍超时与消息上限
  • 工具描述文案要更新（README、schema description），总数不变
